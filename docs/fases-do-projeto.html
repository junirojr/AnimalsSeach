Ambiente + Documentação Inicial

A fundação: nada compila ou roda sem isto

Sobe a infraestrutura local (Docker), cria a solution .NET com os 4 projetos de camada, inicializa o Next.js e monta o esqueleto de documentação (CLAUDE.md por camada + 4 quadrantes Diataxis).

Por que importa

Define as regras do jogo antes de uma linha de lógica: idioma do código (português sem acento), padrão de commits, regra de dependência entre camadas. Erros de fundação se propagam por todo o projeto.

Como se relaciona

Cria os contêineres (PostgreSQL+pgvector e Ollama) que as fases 2 e 5 vão usar, e a estrutura de pastas que todas as fases seguintes preenchem. Os CLAUDE.md orientam a IA em cada camada.

Principais arquivos

docker-compose.yml — pgvector/pg16 + ollama backend/Buscador.slnx — solution + 4 projetos CLAUDE.md (raiz + por camada) docs/ — tutorials / how-to / reference / explanation / ai

Pontos de melhoria

  • Não há CI (GitHub Actions) rodando build+testes a cada push.
  • Slash commands previstos (/seed, /embeddings) e docker exec ollama ollama pull não estão automatizados num script de bootstrap.

Domain Layer

O coração das regras de negócio — sem dependências externas

Modela o domínio puro: classes base (Entidade, RaizAgregada, ObjetoDeValor), o agregado Animal com fábrica Criar, o value object AnimalId, os enums (Dieta, Habitat, StatusConservacao) e a interface IRepositorioAnimal.

Por que importa

É a única camada que nunca referencia EF Core, Npgsql ou MediatR. Isolar as regras torna o negócio testável sem banco e protege contra acoplamento — trocar PostgreSQL por outro banco não toca aqui.

Como se relaciona

Fica no centro da regra Domain ← Application ← Infrastructure ← Api. A Application orquestra estes objetos; a Infrastructure implementa IRepositorioAnimal. Os campos de busca (VetorBusca, Embedding) ficam de fora — entram como shadow properties na Fase 2.

Principais arquivos

Domain/Animais/Animal.cs — agregado + Criar Domain/Animais/AnimalId.cs — value object Domain/Animais/{Dieta,Habitat,StatusConservacao}.cs Domain/Animais/IRepositorioAnimal.cs Domain/Comum/{Entidade,RaizAgregada,ObjetoDeValor}.cs

Pontos de melhoria

  • Não há eventos de domínio (domain events) — útil se o projeto crescer.
  • Validações de invariantes no Criar poderiam ser mais ricas (ex.: tags não vazias).

Infrastructure — Banco de Dados

Onde o domínio encontra o PostgreSQL

Implementa ContextoBanco (EF Core + Npgsql + pgvector), a configuração Fluent AnimalConfiguracao (mapeia a tabela animais, enums como texto, e as shadow properties search_vector/embedding), as migrations com índices GIN (FTS) e HNSW (vetores), e o RepositorioAnimal.

Por que importa

Traduz o domínio limpo para tabelas reais sem poluir o Domain. As shadow properties são a chave: o banco sabe de tsvector e vector(1024), mas a classe Animal não.

Como se relaciona

Implementa o contrato IRepositorioAnimal da Fase 1. Os índices GIN e HNSW criados aqui são o que torna as buscas das Fases 4–6 rápidas. Os testes usam Testcontainers — um PostgreSQL real em Docker.

Principais arquivos

Infrastructure/Persistencia/ContextoBanco.cs .../Configuracoes/AnimalConfiguracao.cs .../Persistencia/RepositorioAnimal.cs Infrastructure/Migrations/*CriacaoInicial* — GIN + HNSW tests/.../Fixtures/ApiTestFixture.cs

Pontos de melhoria

  • 2 avisos de build conhecidos no ApiTestFixture.cs (DisposeAsync oculta herdado; PostgreSqlBuilder() obsoleto).
  • A coluna animais.embedding (vetor único por animal) ficou legada após a adoção do multi-vetor por fragmentos.

Application Layer

Casos de uso em Vertical Slices (CQRS com MediatR)

Cada caso de uso vive em sua própria pasta em Funcionalidades/: consulta/comando + manipulador + validador. Inclui ObterAnimalPorId, ObterAnimais (paginada), PopularAnimais (dados-semente) e os DTOs/mapeamentos em Compartilhado/.

Por que importa

Separa o que o sistema faz (casos de uso) de como faz (Infrastructure). O padrão Vertical Slice mantém cada feature coesa e fácil de achar; o MediatR desacopla a Api dos handlers.

Como se relaciona

Depende só do Domain. Define interfaces (IServicoBuscaTextual, IServicoEmbedding…) que a Infrastructure implementa nas fases seguintes. A Api (Fase 7) só chama mediator.Send(...). A validação roda via ComportamentoValidacao (pipeline).

Principais arquivos

Application/Funcionalidades/PopularAnimais/ — Comando + DadosSementeAnimal .../ObterAnimais/ · ObterAnimalPorId/ Application/Compartilhado/ — DTOs, interfaces, FusaoRrf Application/Comportamentos/ComportamentoValidacao.cs

Pontos de melhoria

  • Não há paginação com metadados (total, páginas) — só itens.
  • Mapeamento DTO manual; poderia usar um mapeador se a quantidade crescer (hoje manter manual é mais didático).

Full-Text Search (FTS)

Busca por palavras-chave nativa do PostgreSQL

Um gatilho preenche search_vector (to_tsvector em portuguese) automaticamente a cada INSERT/UPDATE. O ServicoBuscaTextual consulta com tsquery e ranqueia por ts_rank.

Por que importa

É a busca léxica: rápida, exata, ótima para termos específicos (nome, tag). Serve de baseline e de uma das duas pernas da busca híbrida. Roda inteiramente no banco, sem IA.

Como se relaciona

Usa o índice GIN da Fase 2 e implementa IServicoBuscaTextual da Fase 3. É o primeiro modo de BuscarAnimais. Mais tarde (F6.1) ganhou recall: OR entre termos + unaccent + indexação de mais campos (distribuição geográfica, tags).

Principais arquivos

Infrastructure/Busca/ServicoBuscaTextual.cs Migrations/*GatilhoVetorBusca* Migrations/*RecallFtsUnaccentMaisCampos* (F6.1) Application/Funcionalidades/BuscarAnimais/ docs/explanation/how-fts-works.md

Pontos de melhoria

  • Não há realce (ts_headline) dos trechos que casaram.
  • Pesos por campo (setweight) dariam mais relevância ao nome vs. curiosidades.
tsvector / tsqueryts_rankunaccentGatilho SQL
5

Busca Semântica

Busca por significado com embeddings e pgvector

O ServicoEmbeddingOllama gera vetores via Ollama; o GerarEmbeddingsComando popula o banco; o ServicoBuscaSemantica busca por distância de cosseno (<=>). Evoluiu por etapas até a estratégia multi-vetor.

Por que importa

Encontra resultados por sentido, não por palavra: "predador dos oceanos" acha "tubarão" mesmo sem o termo aparecer. É a perna semântica da busca híbrida.

Como se relaciona

Usa o índice HNSW da Fase 2 e o Ollama da Fase 0. A geração de embeddings grava via SQL cru (pgvector não tem tradução LINQ). A busca alimenta o modo semântico e, junto da FTS, a Fase 6.

Principais arquivos

Infrastructure/Embeddings/ServicoEmbeddingOllama.cs Application/.../GerarEmbeddings/FragmentadorAnimal.cs Infrastructure/Busca/ServicoBuscaSemantica.cs Infrastructure/Embeddings/ServicoPersistenciaFragmentos.cs docs/explanation/how-embeddings-work.md

Pontos de melhoria

  • Re-geração é "tudo ou nada" por animal (só processa quem não tem fragmento); não há atualização incremental por campo alterado.
  • Não há cache do embedding da consulta (cada busca chama o Ollama).
A jornada da qualidade semântica (vários commits): prefixos do nomic → incluir Nome+Tags no texto → multi-vetor por fragmentos (1 animal → N vetores, busca por max-sim com MIN(... <=>)) → troca do modelo para bge-m3 (1024 dim, multilíngue, sem prefixos) → tags contextualizadas ("NomeComum: tag") para evitar empate de chunks.

Busca Híbrida (RRF)

O melhor dos dois mundos: léxico + semântico

O ServicoBuscaHibrida roda as buscas textual e semântica em paralelo sobre um pool de candidatos e funde os rankings com Reciprocal Rank Fusion (FusaoRrf): score = Σ 1/(k+posição), k=60, normalizado para 0–1.

Por que importa

FTS é exata mas "burra"; semântica é esperta mas difusa. O RRF combina as duas sem precisar comparar escalas de score (usa só a posição) — robusto a outliers e simples de raciocinar.

Como se relaciona

Consome os serviços das Fases 4 e 5; FusaoRrf é função pura na Application (testável sem banco). É o terceiro e principal modo de BuscarAnimais.

Principais arquivos

Application/Compartilhado/FusaoRrf.cs — função pura Application/Compartilhado/IServicoBuscaHibrida.cs Infrastructure/Busca/ServicoBuscaHibrida.cs docs/explanation/rrf-algorithm.md (stub a preencher) docs/comparativos-busca.html — relatório vivo

Pontos de melhoria

  • RRF com peso igual entre as pernas; pesos ajustáveis (tune-search-weights) ainda não implementados nem documentados.
  • Pool fixo (max(limite,20)) — poderia ser configurável.
Sub-fases: F6.1 deu recall ao FTS (OR + unaccent + mais campos) — foi o que resgatou "predador dos oceanos". F6.2 trouxe geração em batch (regeneração 140s → 43s, ~3,2×) e a normalização do score RRF para 0–1.

API Layer

A porta HTTP — fina, sem regra de negócio

Os 5 endpoints vivem em EndpointsAnimais.cs (extensão MapearEndpointsAnimais); o Program.cs é só wiring. Inclui Scalar (OpenAPI), CORS para o frontend e tratamento global de erros (IExceptionHandler: ValidationException → 400, resto → 500).

Por que importa

Expõe a aplicação ao mundo de forma consistente. Cada endpoint faz 3 coisas: lê input, chama mediator.Send, devolve Results.*. O handler global garante respostas de erro padronizadas (ProblemDetails).

Como se relaciona

Topo da pilha de dependências; só conhece a Application via MediatR. O CORS aqui libera a origem do frontend da Fase 8. O Scalar permite testar manualmente todos os modos de busca.

Principais arquivos

Api/Endpoints/EndpointsAnimais.cs Api/TratamentoErros/ManipuladorGlobalExcecoes.cs Api/Program.cs — wiring (~31 linhas) docs/reference/api-endpoints.md

Pontos de melhoria

  • Sem autenticação/rate-limiting (ok para projeto local).
  • Sem versionamento de API nem health-check endpoint.

8

Frontend Next.js

A interface que dá rosto à busca

App Router + TypeScript + Tailwind + TanStack Query. A página eleva o estado (termo + modo) e distribui para BarraBusca (debounce), AlternadorModo (Textual/Semântica/Híbrida), grid de CartaoAnimal e o DetalheAnimal. Testes com Jest+RTL+MSW e E2E com Playwright.

Por que importa

Transforma a API num produto usável. Permite comparar visualmente os 3 modos de busca — o objetivo de aprendizado central do projeto.

Como se relaciona

Consome GET /api/animais/buscar via services/animais.ts (TanStack Query). Os enums chegam como números e são traduzidos pelos mapas em types/animal.ts (ordem espelha os enums do Domain). MSW mocka a API nos testes de componente.

Principais arquivos

frontend/src/app/page.tsx — orquestra tudo components/busca/{BarraBusca,AlternadorModo}.tsx components/animais/{CartaoAnimal,DetalheAnimal}.tsx services/animais.ts · types/animal.ts e2e/busca.spec.ts (Playwright)

Pontos de melhoria

  • Sem realce dos termos casados nem indicador de qual perna (FTS/semântica) trouxe o resultado.
  • Sem paginação/scroll infinito na UI (limite fixo).
  • Inconsistência de versão do Next nos docs (raiz diz 15, frontend/CLAUDE.md diz 16).

Verificação Final

Catálogo cheio, fluxo ponta a ponta provado, docs fechados

Expande o seed de 10 → 52 animais (mamíferos, aves, répteis, anfíbios, peixes, marinhos, insetos/aracnídeos), roda o roteiro de verificação ponta a ponta (infra → migrations → seed → embeddings → 3 modos → testes → frontend → E2E) e preenche a documentação Diataxis.

Por que importa

Com poucos animais, o ranking não diz muito; com 52 a busca híbrida fica significativa e os modos passam a ter diferenças visíveis. É o selo de "funciona de verdade, de ponta a ponta".

Como se relaciona

Exercita todas as fases juntas. O novo seed obriga a re-popular e re-gerar embeddings (Fases 3 e 5); o roteiro toca Api (7), Infra (2,4,5,6) e Frontend (8) numa só passada.

Como tudo se encaixa: as Fases 0–3 constroem a fundação (infra, domínio, banco, casos de uso). As Fases 4–6 são o motor de busca, cada uma adicionando uma capacidade que a próxima combina (léxico → semântico → híbrido). A Fase 7 expõe via HTTP, a Fase 8 dá interface, e a Fase 9 enche o catálogo e prova o todo. A regra de dependência Domain ← Application ← Infrastructure ← Api se mantém de ponta a ponta — é o que permitiu trocar o modelo de embedding ou dar recall ao FTS sem tocar no domínio.
