Visão geral

A Fase 8 construiu toda a interface de busca que conversa com a API .NET (Minimal API) desenvolvida nas fases anteriores. O trabalho foi feito por um orquestrador que delegou cada edição de arquivo a subagentes especializados, validando cada etapa com npm run build (e npm test quando havia testes) antes de criar o commit correspondente.

Foram 7 etapas, cada uma com seu commit semântico (Conventional Commits):

  2. T8.2 — Tipos TypeScript + serviço de acesso à API

Como os dados fluem

Usuário digita → BarraBusca (debounce 400ms) → page.tsx (estado: termo + modo) → useQuery / TanStack → buscarAnimais() → API .NET :5024 → grid de CartaoAnimal → DetalheAnimal (modal)

Contrato da API consumida

EndpointDescrição
GET /api/animais/buscar?q={q}&modo={Textual|Semantica|Hibrida}&limite={n}Busca → ResultadoBusca[] (q vazio → 400)
GET /api/animais/{id}Um animal → Animal ou 404
GET /api/animais?pagina={n}&tamanho={n}Lista paginada → Animal[]
Atenção aos enums: os campos dieta, habitat e statusConservacao chegam como números (enums serializados). Foram criados mapas int → rótulo PT lendo a ordem real de declaração dos enums em backend/src/Buscador.Domain/Animais/:

  • Habitat: 0 Floresta · 1 Oceano · 2 Deserto · 3 Savana · 4 Montanha · 5 Água doce · 6 Polar
  • StatusConservação: 0 Pouco preocupante · 1 Quase ameaçado · 2 Vulnerável · 3 Em perigo · 4 Criticamente em perigo · 5 Extinto na natureza · 6 Extinto

  • Script "test": "jest" no package.json.
  • frontend/jest.config.ts · jest.polyfills.ts · jest.setup.ts (novos)
  • frontend/tests/mocks/handlers.ts · server.ts (novos)
  • frontend/src/components/**/*.test.tsx (novos)
  • frontend/tsconfig.json (chave ts-node p/ carregar a config .ts)
O ponto mais espinhoso da fase (MSW v2 + Jest + jsdom). Foi necessário, em ordem:
  • Polyfills de Web APIs que o jsdom não expõe (via undici e módulos do Node): TextEncoder/Decoder, ReadableStream/TransformStream/WritableStream, fetch/Request/Response/Headers, MessagePort e BroadcastChannel. Usando require() (não import) para garantir a ordem: definir os globais antes de carregar o undici.
  • Globais definidos com configurable: true — o MSW redefine alguns (ex.: Request) ao iniciar.
  • O next/jest sobrescreve transformIgnorePatterns; como o MSW v2 e suas dependências são ESM puro, a config foi pós-processada para reaplicar o padrão e permitir transformá-las.
  • export {} em jest.polyfills.ts para o TypeScript tratá-lo como módulo (senão os const colidem com os tipos globais do DOM no next build).
Resultado: 2 suítes, 2 testes ✓ com saída limpa (exit 0).

▶️ Como rodar localmente

1) Subir a infraestrutura e o backend (na raiz e em backend/):

# na raiz do projeto
docker compose up -d
docker exec ollama ollama pull bge-m3

# em backend/
dotnet ef database update --project src/Buscador.Infrastructure --startup-project src/Buscador.Api
dotnet run --project src/Buscador.Api   # sobe a API em http://localhost:5024

2) Semear os dados e gerar os embeddings (uma vez):

POST http://localhost:5024/api/animais/popular
POST http://localhost:5024/api/animais/embeddings/gerar

3) Rodar o frontend (em frontend/):

# em frontend/
npm run dev        # abre http://localhost:3000
npm run build      # build de produção
npm test           # Jest + RTL + MSW (não precisa do backend)
npx playwright test  # E2E (precisa de backend semeado + frontend no ar)
Resumo das dependências: os testes de componente (npm test) não precisam do backend — o MSW intercepta as chamadas. Já o teste manual na tela e o E2E (npx playwright test) precisam do backend rodando em http://localhost:5024 com dados semeados.
